Integration preview / Reference implementation

Your application owns the work. The program enforces the payment terms.

The payer authorizes the hold. The merchant signs each capture or unused-balance release. The payer signs reclaim at or after the capture deadline. Your application decides what work to perform and when to charge.

A funded authorization cannot be topped up or extended. New terms require a new authorization. Capture ends strictly before the stored deadline; payer reclaim opens at that deadline for the remaining hold.

A separate paid-report reference

The reference paid report uses synthetic data and fixed charges of 40 and 25 from a 100-token hold, then releases 35. Both artifacts are withheld until every payment step is proven and the complete response is durably saved. It is separate from the payment lab.

Completed-response retrieval is read-only. An unfinished run can block the isolated instance across restarts; there is no automatic retry, refund or resume. Preserve original records when an outcome is pending or UNKNOWN. A timeout does not establish failure.

Assets, costs and recovery

Classic non-native SPL Token assets only; Token-2022 and wrapped SOL are outside this profile. Protocol fees are zero; network transaction fees and permanent payment/vault account rent remain.

The program allows direct payer reclaim without merchant or facilitator participation. The browser still uses application routes to prepare and submit reclaim. With that server unavailable, use the existing standalone wallet-signed tooling; payer consent, configured trusted RPC, fees, usable accounts and original journal custody are still required.

Refunds are a separate operation

A refund returns already-captured funds from the merchant. It requires merchant consent, liquidity and an open refund window. Releasing unused escrow is a different operation.

The SVM auth-capture profile is a local extension, not a published drop-in SDK or a claim of standard SVM interoperability.
